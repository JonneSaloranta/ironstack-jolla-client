# Compatibility with IronStack

How the app's training features line up with IronStack's web UI and its
REST API (`/api/v1/`, checked against IronStack 1.29.0 and
`docs/api/openapi-v1.yaml` there). Scope: everything the API offers -
training, body measurements, activities, stretching and nutrition. Parts
of the web with no API (social, coaching, assistant, tutorials) can't be
built: IronStack #37.

Status: **done**, **todo**, or **n/a** (not possible over the API; listed
so it isn't rediscovered).

## API usage

| Item | Status | Notes |
|---|---|---|
| `Idempotency-Key` on queued `POST`s | done | One UUID per queued write, kept on disk with it, so a retry after a lost response doesn't log a set twice. `422` (same key, different request) is dropped like any other 4xx. |
| `exercise_name` on prescriptions, performed exercises and records | done | No per-id `exercises/<id>/` lookups any more. |
| `sessions/?status=` | done | Dashboard asks for `in_progress` directly instead of scanning the newest page. |
| `exercises/?page_size=100` | done | Fewer requests for the exercise picker. |
| `exercises/?search=` | n/a | Deliberately not used: it matches names in the IronStack profile's language, the app shows them in the phone's. The picker searches the whole list locally, by the name as shown and as stored. |
| `exercises/<id>/last-performance/` | done | "Last time" per exercise, instead of searching the newest page of sessions. |
| `performed-exercises/<id>/suggestion/` | done | Shown in training mode and used as the first set's default, like the web. |
| `up-next/` | done | Dashboard "Up next" card with one tap to start it. |
| `analytics/achievements/` | done | Dashboard, one at a time, moving on every 4.5 s like the web's carousel (or on a tap). Shown to everyone, as on the web; the server already leaves out people who opted out. |
| Ignore unknown response fields | done | Required by IronStack's versioning rules; the app only reads the fields it knows. |

## Behaviour that should match the web

| Item | Status | Notes |
|---|---|---|
| Built-in content names translated | done | The server stores built-in names (exercises, programs, workouts, measurement and activity types, stretches, meal slots) in English and the web translates them with its own catalog (`apps/*/i18n_content.py` + `locale/*/django.po`). The API returns the English names, so the app ships the same translations, generated by `tools/content-i18n/generate.py` (`content.js` for names, `content_texts.js` for instructions). Custom names are shown as typed. A translated name from the API would make this unnecessary: IronStack #36. |
| A missing API key permission explained | done | A 403 names the context and permission to add (e.g. "nutrition - Create"), see `ApiClient::contextForPath`. |
| Default for the next set | done | Same order as the web (`apps.workouts.views._build_set_form`): last set this session, then the smart suggestion (first set only), then the plan's target with `min_reps`. Two additions: after warm-ups only, the first working set's default is used instead of repeating the warm-up, and "last time" fills in when there's nothing else (the web leaves it empty). |
| Smart suggestion shown | done | "Suggested: 52.5 kg x 5 - High confidence" and the reason, until the first working set is logged; in training mode and the full view. The reason text comes in the IronStack profile's language. |
| Per-hand weights | n/a | The web doesn't mark them when logging either (only on the exercise page), so neither does the app. |
| Exercise library | done | Browse, search (shown and stored name) and filter by primary muscle group like the web; muscle groups, equipment, movement type and weight logging shown translated. |
| Exercise guide (description, instructions, images) | done | `exercises/<id>/`, instructions translated with the web's catalog (`content_texts.js`); opened by tapping the exercise's name in training mode or the full view, like the web's guide button. |
| Own exercises | done | Create, edit, deactivate (`DELETE` is a soft delete, like the web's Deactivate). Adding images: n/a, the API takes no uploads. |
| Records for an exercise | done | On the exercise page (`records/`, filtered here). |
| Strength trend | done | Estimated 1RM (Epley, best working non-failure set per day), sessions and volume for the web's date ranges, worked out from completed sessions (IronStack #35). |
| New personal record shown after logging a set | done | A notification like the web's toast: "New PR - <exercise>" and each record. `POST sets/` doesn't return them (IronStack #30), so once a queued set reaches the server the newest `records/` with the set's `performed_at` are shown. |
| Deleting a workout from history | done | `DELETE sessions/<id>/` (records are rebuilt by the server, like the web's delete). |
| Summary period | done | Dashboard: 7 days, 30 days or all time (`analytics/summary/?range=`); tap the heading. The web's "this week" has no API range. |
| Profile settings | done | Units, language, time zone, height, BMI, sharing activity, friend requests and group invites (`PATCH profile/`). The web-only look (theme, appearance) isn't shown. |
| Remaining time estimate in training mode | n/a | Not in the API. |
| Program editing (programs, workouts, prescriptions) | done | Create, edit and delete your programs; add, edit, reorder (up/down, like the web) and delete workouts and their exercises. Weights in your unit, like the web form. Built-in program descriptions translated like the web. |
| Copying a program template | done | No copy endpoint (IronStack #32): done request by request, and a half-made copy is deleted if a request fails. |
| Social, coaching, assistant, tutorials | n/a | No API. |

## Other areas

| Area | Status | Server gaps |
|---|---|---|
| Body measurements | done | Types with their latest reading (body weight first, then by the name as shown); a type's BMI card, statistics, trend and readings; log, correct and delete readings; your own types created and deactivated. Dashboard: body weight and "Log body weight", like the web. Every reading is fetched and grouped here - no type or date filter: #29. Online only - no idempotency key: #31. The 14-day "Time to log your body measurements?" reminder is on the home page; its on/off switch is the app's own (Settings), as the web's isn't in the API profile (#40), and it needs at least one reading because the API doesn't say when the account was made (the web counts from then). |
| Activities | done | Types with how many are logged; a type's summary (count, total duration, distance, calories), duration trend and activities; log (duration in minutes and distance in km/mi, like the web form), correct and delete; your own types created and deactivated. Every activity is fetched and grouped here - no type or date filter: #29. Online only - no idempotency key: #31. |
| Stretching | done | Home with streak, last 7 days, all time, routines, minutes per week and recent sessions; the stretch library (type and muscle group filters, instructions translated) with your own stretches; routines with their stretches, your own created, edited (stretches added, changed, reordered, removed) and deactivated, built-in ones copied to edit (request by request, #32); history with corrections and deletes; log stretching after the fact. A guided session (get ready, hold per side and set, rest, pause, skip) plays on the phone with the web's sequencing and is logged as done with its routine and time - the API can't run a guided session or record per-stretch results (#34). The timer chimes like the web's (same tones, generated by `tools/sounds/generate.py`; off in Settings) - this needs the sailjail `Audio` permission, which Sailfish shows as "Play and record audio" although nothing is recorded. Not here: the cool-down suggestion after a workout (`after_workout` is read-only, #34), and abandoned guided sessions (nothing is logged). |
| Nutrition | done (every part tried in the emulator 2026-11-03; not yet on the phone) | Overview (today vs. target, goal, today's plan); food diary by day with meals, totals, food/recipe/quick entries, edits, deletes, copy day, save meal as recipe; foods with the full label and your own foods; recipes with ingredients; goal, target and nutrition profile (profile editable); diet plans generated, activated, applied to a date, renamed, deleted, with the shopping list, shopping days and ticks kept per plan and trip like the web's; the web's calculators. Gaps: no diary date filter #26, entry nutrition worked out from today's foods #27 (an entry of a built-in or deleted recipe - a diet plan's, say - shows as such, isn't counted and isn't copied: recipes/ lists only your own active recipes), no food search #28, goals/targets read-only #33, online only #31, built-in recipes unreadable #38, null food/recipe crashes the server #39 (worked around). Statistics like the web's (last 30 days, the fixed periods, daily calories with the target line), worked out from the whole diary. On the overview, "Is your current target working?" and the observed maintenance, ported from the web (`suggestions.py`, `maintenance.py`, `trends.py`) and checked against the server's own figures for the same data; accepting a suggested target isn't possible (#33), the page says to do it on the web. Open Food Facts: search by name or barcode, done by the app itself (the API has no import; `ApiClient::openFoodFacts` only talks to `search.openfoodfacts.org` and `world.openfoodfacts.org`, without the key, within the web's per-minute budgets), and the product saved as one of your own foods per 100 g/ml - Nutri-Score, NOVA group and the OFF id are read-only in the API and get lost, so the web won't refresh such a food from OFF (#41). No barcode scanning with the camera (Harbour has no barcode library); the number is typed. |
| Training analytics over time | done | The web's Progress page: workouts, training time and volume, body measurement changes, strength trend per exercise, weekly and muscle-group volume, records grouped by exercise (rep records behind "Show more") for the web's date ranges. Worked out from completed sessions, `records/` and every measurement (#35, #29); the exercise list is read for primary muscle groups. |
